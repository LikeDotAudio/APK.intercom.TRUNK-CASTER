Findings

  1. The Python sims never speak Ward-Beck and never use TCP 7879. They speak SNMP, a telnet console, tc_protocol UDP and HTTP. Only the Rust frame-sim talks to the caster on 7879, and docker-compose.sims.yml runs only that.
  2. The port plan matches the brief, and tests check it. Capital i uses 16100+i, 17100+i and 20000+256i. 8x8 frame k uses 36000+k, 37000+k and 43000+16k.
  3. Python bug: the console walk always fails with 'str' object has no attribute 'hex' (fmt_value on str values). The TS port prints the value instead.
  4. launch_all turns an emulator's 400 into a 500 with the text "HTTP Error 400", because urllib raises before reading the body, and the ok check is dead code. I kept this faithfully and pinned it in a test.
  5. The MIB regex registers a bogus IMPORTS object. The owner lookup by device name has no break, so the last match wins. Both are kept for parity.
  6. Docs disagree with the code about ports. The README says the per-vendor maps are on 8081-8085, but the registry uses 8181-8185. Docstrings say the combined map is on 8080, but the registry uses 8180.
  7. Python behaviours that do not map cleanly:
    • Threads become the event loop.
    • threading.Timer becomes setTimeout with unref.
    • Unbounded ints become BigInt in the BER code.
    • random.Random(1234) becomes PyRandom (an MT19937 port).
    • json.dumps becomes pyJson.
    • str(KeyError) quoting becomes PyKeyError.pyStr.
    • numpy is optional in Python, so audio was optional; in TS the audio series is always on.

How to wire it in

None of these steps has been applied.

  1. Stop the Python launcher first. It holds ports 8180-8185 and every world port.
  2. Run the launcher from Node. cd TYPESCRIPT && node --experimental-strip-types simulator/src/launch-all.ts uses the same emulators.json and the same ports. --list shows which runtime each vendor gets, and --runtime python restores the old behaviour.
  3. Run the RTS estate directly. Use node --experimental-strip-types TYPESCRIPT/simulator/src/rts/main.ts with the same flags as rts_intercom_sim.py.
  4. Leave docker-compose.sims.yml alone. It runs the Rust frame-sim, not Python. A node:24-alpine service sketch is in HANDOFF.md, if the estate should ever run in Docker.
  5. Nothing changes for existing clients. trunk_panel.py and the PANELS Stream Deck clients get identical frames and HTTP shapes.
  6. For an esbuild bundle, ship map-page.html next to the bundle or load it as text.

Risks and open questions

  • Socket scale. A full world in one process is about 7.2k UDP sockets plus 376 SNMP and TCP sockets. Per-vendor processes keep RTS at about 2k. Each live matrix mixer runs a 20 ms setTimeout chain, which is subject to Windows timer jitter.
  • Windows reuseAddr. Both stacks can silently double-bind UDP ports, so do not run Python and Node emulators at once.
  • Type dedup with agent 04. These types are defined locally and should move to the sdk: HelloAck, PortState, EstateState, MapDevice, MapLink, Scenario.
  • Open: should the vendor emulators speak Ward-Beck to 7879, as the brief assumes?
  • Open: should the walk crash and the 400→500 problem be fixed in Python too?
  • Open: when, if ever, to retire --runtime python?

frame-sim (Rust): keep it in Rust

It is 253 lines and already right for its job. It shares trunk_caster_sdk::wardbeck with the caster, so parse and format stay single-sourced. One small static image serves 27 compose services. Minor issues to fix in Rust: now() returns epoch seconds, not ISO time, and reconnect backoff has no jitter.
